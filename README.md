# IT-Enterprise: що відомо і чи зможемо ми писати на цій платформі як на Odoo

Стартовий документ окремого репозиторію під IT-Enterprise (ITE). Зібраний за підсумками розмови 20.10.2026.

Джерела:
- **База знань ITE-KB** (MCP-сервер, тільки читання). Її зібрали для команди впровадження Toyota.
- **Наша робота з Odoo 19** у репозиторії `todo_timur` (каталоги `factory3d/`, `odoo_graph/`).

Посилання на базу знань подано як `doc_id` і тип джерела. Типи джерел описано в §1.2.

## 1. Що таке IT-Enterprise

### 1.1 Продукт загалом
- **Що це.** Українська ERP-система однойменного вендора. Платформа називається **ITnet2**.
- **Для кого.** Середні й великі підприємства.
- **Що покриває.**
  - бухгалтерський і податковий облік;
  - кадри й зарплату;
  - склад (ТМЦ), основні засоби;
  - виробництво (планування, PDM/техмаршрути);
  - закупівлі й тендери (інтеграція з публічними закупівлями і SmartTender);
  - електронний документообіг (SmartManager, електронний архів), договори.
- **Варіанти клієнта:**
  - тонкий Windows-клієнт (протоколи tcp/http);
  - веб-клієнт IT.Web 2016, працює в браузері.

  Джерело: help, doc_id=131648.

Загальне тло вище написане із загальних знань. Усе далі підтверджено базою знань.

### 1.2 База знань ITE-KB
З чого зібрана (ite_guide):

| Джерело | Що це | Надійність |
|---|---|---|
| `instr` | інструкції, пройдені в живій системі | найвища |
| `help` | офіційна довідка вендора; у базі лише перші ~500 символів теми, повний текст лежить на сервері ENTERPRISE-WEB | висока, але неповна |
| `forms` | картки форм: поля, типи, звіти | |
| `code` | класи й методи декомпільованого ITnet2, що працюють з БД | |
| `libs` | описи декомпільованих бібліотек; частково побудовані автоматично за іменами класів і namespace'ів | |
| `claude` | робочі знахідки; подавати як «за спостереженнями» | гіпотези |

Пріоритет при суперечностях: `instr > help > forms > code > claude`.

Свіжість: тексти й код станом на вересень–жовтень 2026. Найкраще покриті бухоблік і зарплата, решта — переважно довідкою й кодом.

Інструменти:
- `ite_search` — пошук. Запит писати **українською**, коротко, бухгалтерськими термінами.
- `ite_get_document` — повний текст документа.
- `ite_form_fields` — поля форми чи довідника.
- `ite_table_usage` — хто читає й пише таблицю.
- `ite_find_class`, `ite_code_context` — клас і його виклики.

## 2. Карта можливостей конкретної інсталяції

Джерело: instr «0. Карта можливостей: що працює, а що ні», doc_id=134898.

### 2.1 Працює повністю, від документа до проводки
- **Каса:** видача, надходження, підзвіт, повернення залишку й перевитрати.
- **ТМЦ:** надходження, списання, реалізація, повернення в обидва боки, інвентаризація.
- **Послуги:** надані й отримані.
- **ОЗ:** картка, прихід, введення в експлуатацію.
- **Валюта.**
- **ПДВ:** податкова накладна й коригування.
- **Початкові залишки.**
- **Звітність:** ОСВ, аналіз рахунку, картка рахунку, журнал-ордер, шахматка.
- **Кадри й зарплата:**
  - особова картка, призначення, штатний розпис, щорічна відпустка, табель;
  - нарахування, розрахунок, ПДФО, ЄСВ;
  - виплата через касу (платіжна відомість і видатковий ордер);
  - проводки по зарплаті, додаток 4ДФ.

  Працює лише при відкритому розрахунковому місяці. Без нього не створюється навіть табель.

Перевірка узгодженості: у зведеній ОСВ дебет дорівнює кредиту.

### 2.2 Де впирається в налаштування впровадження
Ознака завжди одна: документ створюється, але розрахунок мовчить або пише протокол про брак налаштувань.

| Ділянка | Причина |
|---|---|
| Банківська виписка | порожній рахунок обліку: не задано прив'язку «банківський рахунок → 311» |
| Знос ОЗ | метод обмежений переліком об'єктів обліку |
| Закриття місяця | регламентний документ прив'язаний до застарілої господарської операції |
| Книга продажів | не задано звітний місяць податкового обліку |
| Кадрові накази | у базовому екрані немає додавання; екрани за типами наказів падають з помилкою (решта кадрового контуру працює) |
| Оклад у картці | прихований параметром доступу (`HRUSERGRP`); обхід — разове нарахування |
| Військовий збір | вид розрахунку є, але в довіднику нарахувань і утримань його немає |
| Лікарняні, розрахунок за середнім, додаткові відпустки | довідник відповідності посилається на неіснуючі види нарахувань |
| Безготівкова виплата | порожній довідник «Тип рахунку» |
| Індексація | не заведено індекси інфляції |

### 2.3 Не впроваджено зовсім
- **Виробництво:** немає варіантів обліку для 23/26 і номенклатури готової продукції.
- **Взаємозалік:** тип є, жодного проведеного прикладу.
- **МСФЗ:** довідники порожні.
- **Автотранспорт:** у господарських операцій немає статей.

Це не «зламано», а «не впроваджено»: усе вмикається налаштуванням.

### 2.4 Корисні прикмети
- **Помилки «тихі».** Кнопка спрацьовує, повідомлення немає. Підказку, якого поля чи налаштування бракує, шукайте в рядку стану внизу й на синіх плашках над ним.
- **Помилка 1713** («Недопустима ширина поля або дробової частини»). Пункт веде в старий шар (VFP), який веб-клієнт не підтримує (claude, doc_id=134557).
- **«Запис не знайдено» на свідомо правильному коді, і F10 не відкриває довідник.** Перелік допустимих значень задано описом екрана, а його не видно ні в довідниках, ні в правах.
- **«Пункт меню є» нічого не гарантує.** Меню будується з реєстру, спільного для всіх інсталяцій. Працездатність залежить від даних налаштування.
- **Порядок впровадження:** об'єкт обліку → план рахунків → аналітики рахунків → підрозділи й виконавці → варіанти обліку для складських рахунків → початкові залишки → документи.
- **Перевірка ділянки до роботи:** знайти вже проведений документ того самого типу й подивитися, які поля в ньому заповнені.

## 3. Архітектура (реконструкція)

Офіційний опис є лише для топології: довідка D-AD-ADM-D «Архітектура IT-Enterprise» (help, doc_id=131643). Внутрішня будова сервера нижче — реконструкція за описами декомпільованих бібліотек (`libs`) і спостереженнями в живій системі. Звірена з базою знань версія, яку ведемо далі, — [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md).

### 3.1 Шари

**1. Клієнт — тонкий.** Уся логіка на сервері. Приклад: у діалогового рушія Sted2 серверна частина — 4 047 методів, клієнтська — 275 (libs, doc_id=124206). У БД клієнт майже не звертається (doc_id=124210). Логіка на клієнті лише там, де без машини користувача не обійтися (doc_id=124195):
- КЕП (ключ лежить у користувача);
- обладнання через COM-порт (ваги, сканери, РРО);
- автотести інтерфейсу.

**2. Сервер додатків.**
- Windows-служба `ITnet2.Server.Launcher.exe`, по одній на інстанс. У нашій інсталяції це `ITnetSvc.master` і `ITnetSvc.prom`, порт 8222 (claude, doc_id=134561).
- `ITnet2.Server.SessionCore`: сесія, налаштування, ліцензування, ЕЦП, аудит змін БД, OCR (doc_id=124280).
- Меню будує `MainMenuService` з таблиць `MENU`, `MNU`, `ARMM`, `MELU`, `UST`, `USTZ` (code, doc_id=108824).

**3. Бізнес-логіка.**
- **`ITnet2.Server.BusinessLogic.Core`** — платформний шар: 4 085 файлів, ~17 000 методів, 905 таблиць (doc_id=124230). У ньому:
  - модель документа та її налаштування (`Documents`, `DocumentConfig`);
  - пакети конфігурацій (`Configuration`): публікація, експорт та імпорт, SQLite-пакети;
  - матриця ролей (`RolesMatrix`);
  - маршрути узгодження (таблиці `AG*`);
  - шина подій (`EventModel`, `ServicesManagementSystem` — найбільший клас системи);
  - рушій налаштовуваних розрахунків `ArbitraryCalculation`: формули на динамічних змінних, проміжні результати в тимчасових таблицях;
  - НДІ і перекодування довідників;
  - інтеграції: обмін документами між організаціями (`FileSharingService`), електронна ТТН, Kubernetes;
  - планувальник, бекапи, вбудоване тестування конфігурацій і звітів (`Tests`).
- **Предметні модулі** — окремі збірки:
  - `BusinessLogic.LP` — тендери (doc_id=124239);
  - `BusinessLogic.MP.PDM` — техмаршрути (doc_id=124248);
  - `BusinessLogic.FI` — бухгалтерія: створення проводок, ОЗ, XBRL, акцизи (doc_id=124233).
- **`Runtime.Methods`** — методи, прив'язані до сутностей за кодом таблиці: `DMZ`, `DMS`, `PLA`, `SP2`, `KSM`, `DOG`, `ORG`, `TASKS` (doc_id=124256, 124278). Платформа викликає їх динамічно.
  - `F2<…>UserRequestMethod` — за дією користувача (кнопка на формі);
  - `Anycall<…>AnyCallMethod` — звідки завгодно: з конфігурації, формул, сценаріїв;
  - механізм лежить у `Server.Runtime.Methods` (64 файли), реалізації — у `BusinessLogic.Runtime.Methods` (5 743 файли).

**4. Екрани будуються з метаданих** (doc_id=124203):
```
Client.Controls.ScrEdit          → користувач малює екран
Server.Dialogs.Menuget.Designer  → серверна частина дизайнера, зберігає в SCRZ / SCRS
Server.Dialogs.Menuget           → ScreenBuilder + InputFormCodeGenerator
InputForm / InputForm2           → згенеровані *Base-класи
InputForm/*.cs                   → кастомна логіка успадковується від *Base
```
Робота із записом іде через серверні курсори `<Сутність>Cursor` (doc_id=124231). Наслідок: частина обмежень сидить в описі екрана й не видна ні в правах, ні в довідниках.

**5. Доступ до даних** — `ITnet2.Server.Data` (doc_id=124269).
- Класи `DatabaseManager`, `SqlClientBase`, `SqlClient`, `MsSqlBase`: спільна база й нащадки під конкретну СУБД.
- За системними таблицями в коді видно підтримку **MS SQL, Oracle і PostgreSQL**. SQLite використовується для локальних пакетів, ElasticSearch — для індексації.
- Таблиці названо короткими кодами:

  | Код | Що це |
  |---|---|
  | `DMZ` | заголовок документа |
  | `DMS` | рядки документа |
  | `DMT` | типи процесів (тип документа) |
  | `ORG` | організації |
  | `OBJ` | об'єкти обліку |
  | `SP2` | довідник |
  | `DOG` | договори |
  | `SYS` | системна таблиця |

**6. Успадкований шар Visual FoxPro.**
- Ознаки в коді: `It9Handler`, `clearFoxResources` у `MainMenuService`.
- Частина функцій є тільки там, і веб-клієнт їх не виконує:
  - звіти «Аналізу виконання» в договорах;
  - увесь касовий контур роздрібу (claude, doc_id=205370);
  - запис `GODMEC_NAL`: .NET-код це поле лише читає (claude, doc_id=135926).

### 3.2 Модель обліку: налаштування, а не код
Ланцюжок: тип документа → господарська операція (`STO`) → статті (`STOT`) → проводки. Плюс варіанти обліку й аналітики рахунків.

«Не працює» тут зазвичай означає «не налаштовано»: в операції немає статей або порожня прив'язка рахунку.

Приклад ручної операції: ТГО 9068 зі статтями `005`, `010`, `015`, `099` (claude, doc_id=134555).

Відома особливість конфігурації — дублі статей. Приклад: схема зарплати 9545, статті 210 і 265 дають подвійну проводку `Дт 661 / Кт 3773` (claude, doc_id=137289, 137299).

### 3.3 Експлуатація
- **Планувальник завдань — не служба сервера додатків.** Його раз на хвилину запускає завдання SQL Server Agent, стартуючи клієнт (`IT2Client2.exe`) під службовим користувачем. Сервер може працювати, а планувальник стояти (instr, doc_id=124188; help, doc_id=131824).
- **Кешування параметрів доступу (`USTZ` / `VARUST`) — питання відкрите.**
  - Інструкція: після зміни параметра потрібен перезапуск служби.
  - Нотатка від 04.10: перезапуск не допоміг (claude, doc_id=134561).
  - Нотатка від 02.10: `MENUACCESS` читається при кожному зверненні, а вміст параметра — ні (doc_id=135215).

### 3.4 Чого ми не знаємо
Звірка з базою знань 20.10.2026 закрила частину пунктів (подробиці й джерела — docs/ARCHITECTURE.md):
- ~~Протокол і транспорт клієнт–сервер~~ — тонкий клієнт працює через .NET Remoting, сеансом керує сервер (§2.2).
- ~~Типову топологію розгортання й масштабування~~ — серверів додатків скільки завгодно; оновлення ставиться на master-сервер і реплікується на решту (§2.3).
- Як пакети накочуються між комплектами, тепер відомо: заявки DEV → TEST → PREDPROD → PROD (§6.2). Склад zip теж відомий, але **формат рядків усередині архіву — ні**.
- Ліцензування: USB-ключ на «сервері ключа» (§2.5). Як це лягає на тестовий стенд — невідомо.
- Межа .NET / FoxPro проходить по сутностях: у типу процесу є ознаки `IT10`, `BL9`, `POST10` (§2.4). Повного переліку немає.
- Клієнтські веб-бібліотеки: переважно не розібрані.
- Версія й платформа (9/10/11) нашої інсталяції, чи є GraphQL/REST API.

## 4. Механізми доробки ITE

| Механізм | Що дає | Джерело |
|---|---|---|
| **Бібліотеки коду C#** | свої збірки на C#. Підключаються посиланням «Посилання на збирання користувача» в RRT-методі, виді відображення, інтерфейсі, конструкторі допомоги, планувальнику, екрані | help, doc_id=132453 |
| **RRT-методи** | виклик свого коду на подію об'єкта (наприклад, `ANYCALL` + `AFTERKMAT` — після введення коду ТМЦ). Свій метод починається з `_`; тип VFP або C#; у системних можна змінювати лише «Скасовано», локальну умову й команди | help, doc_id=132241, 128321, 133829 |
| **Свої об'єкти й таблиці** | код починається або закінчується на `_` — аналог `x_` в Odoo | help, doc_id=132240 |
| **Бізнес-логіка на C#** | у довідниках і конструкторах: клас з `override` базових методів | help, doc_id=133994 |
| **Моделі розрахунків, ArbitraryCalculation** | формули й методи після розрахунку з кнопкою Compile | help, doc_id=134003 |
| **Конструктор екранів** | опис екрана в `SCRZ`/`SCRS` → генерація коду | libs, doc_id=124203 |
| **Пакети конфігурацій** | перенесення змін між базами (докладніше нижче) | help, doc_id=132707, 132719, 132685 |
| **Веб-сервіси** | публікація розрахунків системи; перелік публікує адміністратор. Пакетний обмін: `IMPORT.LOADIMPORTEDDATA`, `IMPORT.STARTIMPORT`, `IMPORT.CHECKIMPORTRESULT`, `EXPORT.GETPACKETS`, `EXPORT.GETPACKAGEDATA`, `EXPORT.SETIMPORTSUCCESSFULMARK`, `EXPORT.STARTEXPORT` | help, doc_id=132581, 132829, 132833 |
| **Експорт та імпорт інтерфейсів** | перенесення готових інтерфейсів між базами (режим F2) | help, doc_id=134424 |

Як працюють пакети конфігурацій:
1. Задаємо «об'єкт конфігурації» — набір сутностей.
2. Формуємо пакет: знімок цих сутностей на момент формування. Архів кладеться в службовий каталог сервера додатків.
3. Проводимо пакет на цільовій базі через реєстр заявок або прямим імпортом.

Режими проведення: «тільки додавання й оновлення» або «повна заміна з видаленням рядків». Каталог експорту на клієнт задає параметр `GLCONFIG`.

Для платформи v11 вендор пише, що сервіси спілкуються через HTTP, REST, GraphQL, gRPC, OAuth і єдину шину повідомлень (help, doc_id=131640).

## 5. Наш спосіб роботи в Odoo і як він лягає на ITE

### 5.1 Що робимо в Odoo (репозиторій `todo_timur`)
1. **Спершу документи, потім код.** `factory3d/docs/DOC_STANDARD.md`: за `ARCHITECTURE.md` і `SPEC.md` (FR, AC з типом перевірки, `ВІДКРИТЕ ПИТАННЯ Q-xx`) розробник-агент пише модуль без запитань, а тестувальник-агент пише тести, не читаючи код.
2. **Доробка — вихідний код у git:** модулі Odoo 19 (manifest, Python, XML) з конвенціями `f3d.*`, `f3d_*`, `factory3d.<module>.<param>`.
3. **Data-модуль без Python:** `factory3d_iot_sim` описує моделі `x_*` через XML-записи `ir.model` і `ir.model.fields`.
4. **Заливання й читання даних скриптами через XML-RPC** (`plant/odoo_rpc.py`, `odoo_push.py`, `odoo_pull.py`). Зовнішні ID роблять повторний запуск безпечним.
5. **`odoo_graph`:** граф кастомного шару за метаданими `ir.*` і автоматичний пошук проблем.
6. **Своє середовище:** Odoo в docker compose плюс емулятор обладнання.

### 5.2 Зіставлення

| В Odoo | Аналог в ITE | Переноситься? |
|---|---|---|
| SPEC/ARCHITECTURE, FR/AC/Q, збирання агентами | те саме; методика від платформи не залежить | **Так, повністю** |
| Python-модуль у git | C#: бібліотеки коду, RRT-методи, бізнес-логіка екранів | **Частково.** Код — текст, його можна писати й зберігати в git. Але живе він у базі й вноситься через адмін-інтерфейс, установки «модулем» немає |
| data-модуль з `x_*` | свої таблиці, об'єкти, RRT-методи з `_`; облік через господарські операції й статті | **В ідеї так**, прямий аналог |
| установка модуля на тест і прод | пакети конфігурацій і механізм заявок DEV → TEST → PREDPROD → PROD | **Так, але наосліп:** склад zip відомий, формат рядків усередині — ні; збирати пакет із git поки не вміємо |
| XML-RPC `execute_kw` до будь-якої моделі | веб-сервіси (кожен розрахунок публікується окремо, авторизація через ticket) і пакетний IMPORT/EXPORT | **Гірше:** універсального ORM-доступу немає. На платформі v11 є GraphQL і REST API, але чи розгорнуті вони в нас — невідомо |
| `odoo_graph` за `ir.*` | граф декомпільованого коду вже є в ITE-KB; граф доробок можна будувати за таблицями конфігурації | **Так**, якщо буде доступ на читання до БД |
| docker-стенд | Windows-служба, MS SQL, ліцензія, FoxPro-шар | **Складно:** потрібен стенд від замовника або вендора |

### 5.3 Що заважає найбільше
1. **Немає зворотного зв'язку.** Odoo агент знає глибоко й може запустити локально. По ITE є лише база знань: декомпільований код і обрізана довідка. Живої системи й доступу до її БД в агента зараз немає. Без стенду помилки гарантовані: платформа часто падає мовчки, а обмеження ховаються в описах екранів.
2. **Джерело істини — база, а не репозиторій.** Користувацький код зберігається в полі `BL` таблиці сутності, сервер компілює його сам (help, doc_id=133587). Поки ми не вміємо збирати чи розбирати пакет конфігурації, git буде копією, а не оригіналом.
3. **API для свого C#-коду описано лише прикладами.** У довідці є форма методу `Call(params object[] param)` і параметри джерел `ANYCALL` (help, doc_id=128321). Базові класи RRT-методів і екранів видно тільки через декомпіляцію (`ite_find_class`, `ite_code_context`).

## 6. План: пілот

**Мета:** перевірити повний цикл «SPEC → код у git → внесення в тестову базу → перевірка» на одній маленькій доробці. Наприклад, своя таблиця плюс RRT-метод на C# для одного типу документа.

**Що потрібно, щоб працювати майже як з Odoo:**
- [ ] Тестовий стенд ITE, до якого агент може дотягнутися: веб-клієнт через браузер (Playwright) або хоча б читання MS SQL.
- [ ] Один вивантажений пакет конфігурації — розібрати формат і навчитися збирати його з git.
- [ ] Пара живих прикладів своїх RRT-методів чи C#-бібліотек — звірити API з декомпільованим кодом.
- [ ] Повний текст довідки вендора за розділами «Адміністрування» (D-AD-ADM-*) і «API» (D-IS-API-*): у базі знань він обрізаний.

**Якщо стенду не буде:** агент пише специфікації, код та інструкції, а вносить і перевіряє людина. Це робочий, але помітно повільніший цикл.

**Структура репозиторію** (заведена 20.10.2026; у кожному каталозі є README з правилами):
```
docs/
  DOC_STANDARD.md        ← адаптація factory3d/docs/DOC_STANDARD.md під ITE
  ARCHITECTURE.md        ← платформа (розділ 3 цього файлу), доповнюється в міру перевірки
  modules/<доробка>/ARCHITECTURE.md, SPEC.md
src/
  csharp/<доробка>/      ← C#-код бібліотек і RRT-методів (копія того, що внесено в базу)
  config/                ← розібрані пакети конфігурацій
tools/
  ite_graph/             ← аналог odoo_graph за таблицями конфігурації ITE
```
