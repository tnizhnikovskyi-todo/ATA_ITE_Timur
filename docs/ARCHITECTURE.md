# IT-Enterprise (ITnet2) — архітектурний каркас

Версія 0.1 · 20.10.2026 · агент, за матеріалами ITE-KB. Статус: чернетка до пілота. Цей файл — спільна
основа для документів доробок (`docs/modules/<доробка>/ARCHITECTURE.md` і `SPEC.md`); правила їх
оформлення — у [DOC_STANDARD.md](DOC_STANDARD.md). Карта можливостей нашої інсталяції — у
[README.md](../README.md) §2.

Розвиток розділу 3 README: кожне твердження звірене з ITE-KB 20.10.2026 і має джерело. Позначки:
**підтверджено** — `instr` або `help`; **реконструкція** — лише `code`/`libs`; **за спостереженнями** —
лише `claude`.

## 1. Принцип і стан знань

Працюємо як в Odoo: спершу `ARCHITECTURE.md` і `SPEC.md`, потім код у git, потім внесення в базу й
перевірка. Відмінність одна, і вона визначає все інше: **джерело істини — база ITE, а не репозиторій.**
Користувацький код зберігається в полі бізнес-логіки сутності в БД і компілюється сервером додатків (§5.2);
git — копія, поки ми не навчимося збирати пакет конфігурації з репозиторію (§6, Q-03).

Що знаємо і звідки:

| Шар знань | Стан | Звідки |
|---|---|---|
| Топологія, клієнти, протокол, масштабування | підтверджено | help, розділ D-AD-ADM-D «Архітектура IT-Enterprise» (doc_id=131643) |
| Внутрішня будова сервера додатків | реконструкція | libs, code |
| Механізми доробки (RRT, C#, пакети) | підтверджено в загальних рисах; API — реконструкція | help D-AD-ADM-*, D-IS-API-*; code |
| Поведінка нашої інсталяції | підтверджено частково | instr, claude |

Стенду, до якого дотягується агент, немає (Q-01). Доки його немає, AC доробок перевіряються типами BLD, UT і
MAN (DOC_STANDARD.md, «Правила»), а вносить і перевіряє людина.

## 2. Платформа: офіційний опис

### 2.1 Рівні й компоненти

Трирівнева архітектура клієнт–сервер з версії 9.61: бізнес-логіка на сервері додатків, який стоїть окремо або
разом із SQL-сервером (help, doc_id=132072). Склад серверної частини (help, doc_id=131721):

| Компонент | Призначення |
|---|---|
| Сервер додатків | обслуговує клієнтів; може працювати з кількома локальними файловими частинами |
| Сервер web-додатків | робота з браузера й мобільних застосунків (Android/Apple) |
| Локальна файлова частина | файловий ресурс з бізнес-логікою системи; на одній машині із сервером додатків |
| Мережева файлова частина | синхронізація локальних файлових частин і налаштування доступу до БД; рекомендовано на master-сервері |
| Сервер БД | окрема машина |
| БД системних налаштувань | на основному сервері БД (MSSQL-версія) або в SQL Express на сервері додатків |
| БД великих вкладень | окремо або разом з основною БД (IT Content, help, doc_id=132978) |
| Сервер «Сервісів» | безсесійні мікросервіси на Kubernetes, щонайменше дві ВМ |

Структура каталогів фіксована: на сервері додатків — `Server`, `Logs`, `Local`, `ARMW`, `PRG` (програмні
модулі за контурами й підсистемами), `DBF`, `HELP`, `INI`, `PICTURE`, `PRNT`; на мережевій частині ще `_SETUP`,
`SYSDBF`, `PRNT.NET` (help, doc_id=131721).

### 2.2 Клієнти й протокол

- **Варіанти клієнта:** тонкий Windows-клієнт (tcp або http), web-клієнт IT.Web 2016, web-клієнт IT.WebRMD
  (help, doc_id=131648, 131654). Рядовим користувачам рекомендовано браузер плюс WEB-Агент для пристроїв
  робочої станції (help, doc_id=131721).
- **Транспорт тонкого клієнта — .NET Remoting** на заданому порту, потрібен прямий доступ до сервера
  (help, doc_id=131779). Наш порт 8222 (claude, doc_id=134561).
- **Сеанс керує сервер:** сервер ініціює кожен діалог, передає клієнту його параметри й дані, отримує
  введене й продовжує роботу (help, doc_id=131654). Усі розрахунки на сервері, клієнт — лише введення,
  виведення й друк (help, doc_id=131653).
- **Сервер додатків ↔ БД — SQL-запити**; усі сервери рекомендовано тримати в одній ЛОМ (help, doc_id=131651).

### 2.3 Масштабування й оновлення

- Кількість серверів додатків і web-серверів не обмежена; варіанти — від одного сервера разом із БД до
  кількох виділених серверів і робочої станції як локального сервера (help, doc_id=131655).
- **Master-сервер додатків:** пакет оновлення ставиться лише на нього; кожен інший сервер при старті звіряє
  версію з master і реплікує зміни; клієнт оновлюється при підключенні до будь-якого сервера
  (help, doc_id=132337). Web-ферми оновлюються спеціальним сервісом від еталонної web-частини (там само).
- Розподіл клієнтів між серверами — правилами: сервер або обслуговує клієнта сам, або перенаправляє на інший
  (help, doc_id=131975).

### 2.4 Платформи 9, 10 і 11

- **IT-Enterprise 10** — умовна назва платформи, де сервер і клієнт є компонентами .NET Framework; вона працює
  всередині версії 9 і зберігає виклик коду Visual FoxPro; програмування — у Visual Studio
  (help, doc_id=133486).
- Межа 9/10 видна в даних: тип процесу `DMT` має поля `IT10` «Ознака 10-ї версії», `BL9` «Бізнес-логіка 9-ї
  версії», `POST10` «Ознака розноски 10-ї версії» (forms, doc_id=124883). Отже, перемикання йде по
  сутностях, а не для всієї системи. Це пояснює функції, які веб-клієнт не виконує (README §3.1, п. 6).
- **Платформа v11** — набір сервісів: Application Server і WebRMD як ядро; GraphQL і REST API як
  проміжний рівень; SmartID (OAuth 2.0, OpenID Connect, SSO); RabbitMQ, SignalR, ElasticSearch, OCR
  (Tesseract), ForceBPM, HR Portal, IIoT, APS.Optimizer, моніторинг Prometheus/Grafana, журналювання EFK. Образи
  docker зберігаються в Azure; реєстр сервісів доставляється пакетами оновлення (help, doc_id=131639).
  Сервіси спілкуються через HTTP, REST, GraphQL, gRPC, OAuth (help, doc_id=131640).
- Яка платформа й версія в нашій інсталяції — невідомо (Q-02). Приклад версії в довідці — 20.20.2.0
  (help, doc_id=133587).

### 2.5 Ліцензування

Захист — електронний USB-ключ на одній машині мережі («сервер ключа») і служба, що стежить за ключем і
передає дані захищеній програмі (help, doc_id=131890). Як це впливає на тестовий стенд — Q-08.

## 4. Модель обліку

Тип документа (`DMT`) → типова господарська операція (`STO`, поле `DMT.KSTO`) → статті (`STOT`) → проводки
(`ACCE`); плюс варіанти обліку й аналітики рахунків (README §3.2; forms, doc_id=124883). «Не працює» зазвичай
означає «не налаштовано»: в операції немає статей або порожня прив'язка рахунку. Документи без ТГО проводок
не дають зовсім — наприклад, «Інвентаризаційний опис» (instr, doc_id=134606).

### 5.2 Де живе користувацький код

Підтверджено (help, doc_id=133587):

1. Код пишеться в мемо-полі екрана коригування сутності або в Visual Studio за кнопкою «Редагувати у Visual
   Studio».
2. Visual Studio отримує тимчасовий проєкт у `%TEMP%` профілю користувача; бібліотеки API платформи
   копіюються в `%TEMP%\ITAsseblies\<версія системи>` (написання вендора); після оновлення системи з'являється
   новий підкаталог версії.
3. Після збереження код потрапляє **в поле `BL` таблиці тієї сутності**, для якої він призначений. У файловій
   системі фрагменти коду не зберігаються.
4. Сервер компілює код у динамічну бібліотеку в робочих каталогах сервера додатків.

Наслідки для нас: git — копія полів `BL`; щоб її звіряти, потрібне читання БД (Q-01). Бізнес-логіка кешується:
зміна набирає чинності після виходу в головне меню й повторного входу в інтерфейс (help, doc_id=133632). Є
локальне налагодження з Visual Studio (там само).

### 5.3 RRT-методи

- **Реєстр:** `RRT` «Методи. Перелік», `RRTK` «Методи. Об'єкти», `RRSCT` «Методи. Доступ за розкладом»
  (code, doc_id=109945, 112142). Карток форм `RRT` і `RRTK` в ITE-KB немає — поля невідомі (Q-05).
- **Опис методу:** об'єкт, подія, код (у користувацького завжди починається з `_`), найменування, тип VFP/C#,
  «Посилання на збирання користувача», на вкладці «Додатково» — «Визначити доступ по», «Замінює параметри
  методу», «Модулі». Системні методи коригувати заборонено, дозволено лише ознаку «Скасовано», локальну
  умову й локальні команди (help, doc_id=132241).
- **Події:** `F2` — кнопка «Розрахунки» (help, doc_id=133632); `F12` — виклик за F12 або кнопкою
  «Документи» (help, doc_id=127460); `ANYCALL` «Виклик розрахунку в довільному місці» з джерелом. Прив'язка `ANYCALL`-методу до типів процесів — кнопкою «Налаштування значень»
  (help, doc_id=128321).
- **Джерела `ANYCALL` для `DMZ`** (help, doc_id=128321; перелік обрізаний):

  | Джерело | Коли | Параметри | Повертає |
  |---|---|---|---|
  | `ACCESSMODI` | дозвіл на коригування документа | `param[0]` — `Document` | `true`/`false` |
  | `AFTERENTRF` | після формування проводок | `param[0]` — `Document` | — |
  | `AFTERENTRD` | після видалення проводок | `param[0]` — `Document` | — |
  | `AFTERPOST` | після успішного рознесення | `Document`, `Document.DocumentPosting.PostingParams`, `bool` (скасування) | не аналізується |
  | `BASEFILL` | заповнення реквізитів при введенні на підставі | документ-підстава, новий документ | `false` перериває введення |
  | `BASEROWS` | заповнення рядків при введенні на підставі | документ-підстава, новий документ | `true`, якщо базову логіку перевизначено |
  | `AFTERKMAT` | після введення коду ТМЦ | не описано | не описано |

  `Document` — клас `ITnet2.Server.BusinessLogic.Core.Documents.Document`.
- **Форма C#-методу** (help, doc_id=128321):

  ```csharp
  public override object Call(params object[] param)
  {
      var document = param[0] as Document;
      return true;
  }
  ```

  У прикладах вендора всередині — `SqlClient.CreateCommand("select …", new SqlParam(…)).ExecScalar<int>()`
  і `Settings.Ust.GlDogB.UniversalContractCode` (там само).
- **Ієрархія класів** (реконструкція, libs, doc_id=124278; code): `MethodBase` → `UserRequestMethod`
  (реалізації `F2<…>UserRequestMethod`), `CommandMethod` → `AnyCallMethod`; бізнес-логіка —
  `MethodBusinessLogicBase` → `CommandMethodBusinessLogicBase` → `AnyCallMethodBusinessLogic`,
  `BoolCommandMethodBusinessLogicBase`. Від якого класу успадковується користувацький C#-метод, видно лише в
  заготовці, яку генерує Visual Studio-кнопка (Q-04).
- **Обмеження C#-інтерфейсів:** з них можна викликати VFP-методи лише типів F2 і F12; умови виклику мовою VFP
  не підтримуються — переписати на IronPython або C#, або перенести в тіло (help, doc_id=133479).
- **Відмова за умовою** видна в «Додатково» вікна відповіді, наприклад «Виклик заборонено умовою RRT-методу
  CLRZ.F2.CALCULATE» (instr, doc_id=124169).

## 6. Перенесення змін між комплектами

### 6.1 Об'єкт і пакет конфігурації

- **Об'єкт конфігурації** — таблиця `CNFOBJ`: `CNFOBJID`, `PARENTID`, `NAME`, `KODSYS` (модулі), `COMM`,
  `ISFOLDER`, `ISBLOCKED`, `IMPORTTYPE` («''» — режим вибирає користувач при імпорті, «+» — задає розробник)
  (forms, doc_id=124389). Меню: Адміністрування системи → Управління об'єктами конфігурацій → Створення
  пакетів → Об'єкти конфігурації (help, doc_id=132708).
- **Пакет** — знімок сутностей об'єкта на момент формування; кожне формування дає новий пакет, старі не
  змінюються (help, doc_id=132684).
- **Формат — `*.zip`** (help, doc_id=132708):
  - рядки таблиць заголовків в актуальному стані;
  - рядки пов'язаних таблиць;
  - рядки таблиць перекладів, якщо є;
  - `ExportDetails.txt` — середовище, час створення, список таблиць конфігурації.

  Комплексний експорт кількох об'єктів дає архів у каталозі `FullExport`: файл метаданих і по архіву на
  об'єкт (help, doc_id=132725). **Формат самих рядків усередині архіву невідомий** (Q-03).
- Режими проведення: «тільки додавання й оновлення» або «повна заміна з видаленням рядків»; каталог
  експорту на клієнті — параметр `GLCONFIG` (README §4).

### 6.2 Механізм заявок

Типовий ланцюжок (help, doc_id=132709): пакет формується на **DEV** → заявка в DEV → синхронізація заявок
DEV ↔ TEST → установка й тестування на **TEST** (помилки — заявка повертається «на доопрацювання») →
**PREDPROD** → **PROD**. Статуси пакета по комплектах — таблиця `CONFREQS`: `REQGUID`, `INSTGUID`, `KREQSTS`,
хто й коли встановив, хто й коли підтвердив тестування, `REMARKS`, `INSTINFO` (forms, doc_id=124395).

Рекомендації вендора (help, doc_id=132733): кожен пакет без винятку тестує на TEST команда, що його сформувала;
на PREDPROD тестує фокус-група клієнта; для PREDPROD/PROD обов'язковий опис пакета — що й як тестувати.

Які комплекти є в нашій інсталяції — Q-06: відомі служби `ITnetSvc.master` і `ITnetSvc.prom`
(claude, doc_id=134561), і `master` може означати master-сервер додатків (§2.3), а не окремий комплект.

## 7. Інтеграції

- **Web-сервіси:** публікація викликів розрахунків для читання й введення даних; перелік публікує
  адміністратор (help, doc_id=132581). Виклик у два етапи: авторизація з отриманням ticket, потім сервіс
  (help, doc_id=132828). Web-сервіси мають доступ лише до кількох спеціальних збережених процедур БД; трафік —
  https (help, doc_id=132599).
- **Пакетний обмін:** `IMPORT.LOADIMPORTEDDATA`, `IMPORT.STARTIMPORT`, `IMPORT.CHECKIMPORTRESULT`,
  `EXPORT.GETPACKETS`, `EXPORT.GETPACKAGEDATA`, `EXPORT.SETIMPORTSUCCESSFULMARK`, `EXPORT.STARTEXPORT`
  (help, doc_id=132829, 132833). Конструктор імпорту має бізнес-логіку C# (help, doc_id=132822).
- **Web-розрахунки** на Python, з доступом до системних функцій C# і бібліотек користувача
  (help, doc_id=132586).
- **GraphQL і REST API** (v11) — проміжний рівень, щоб застосунки не залежали від реалізації функціоналу
  (help, doc_id=131639). Це найближче до `execute_kw` в Odoo, але чи розгорнуто в нас — Q-07.

## 8. Тестування засобами платформи

У довідці є розділ «Автоматичне тестування програмного забезпечення» (help, doc_id=132919): модульне
тестування, автоматичне тестування розрахунків, автоматичне тестування інтерфейсів (help, doc_id=132925). Є
механізми підготовки й зберігання тестів, регламентного запуску й розсилки звітів про невідповідності
(help, doc_id=132927). На них спираються типи перевірок ATR і ATI. Повний текст розділу — на сервері
ENTERPRISE-WEB (README §6).

## 9. Експлуатація

### 9.1 Тихі помилки

Кнопка спрацьовує без повідомлення; причину видно в рядку стану й на синіх плашках над ним або в «Додатково»
вікна відповіді, яке закривається само через 2–3 с (README §2.4; instr, doc_id=124169). Тому SPEC доробки
зобов'язаний описати, що бачить користувач при кожній помилці (DOC_STANDARD.md, §12 SPEC).

### 9.2 Параметри доступу: коли діють

| Що змінили | Коли діє | Джерело |
|---|---|---|
| Рівень доступу | після повторного входу: читається раз за сеанс | instr, doc_id=124193 |
| Доступ до пункту меню (`MENUACCESS`) | одразу, читається щоразу | claude, doc_id=135215 |
| Вміст параметра (`VARUST`: `HRUSERGRP`, `PAYLIST`) | інструкція: після перезапуску служби сервера додатків, у вікно без користувачів | instr, doc_id=134984 |

Інструкція має найвищий пріоритет, але за спостереженнями 04.10 перезапуск не допоміг (claude,
doc_id=134561). Питання відкрите (Q-09). До відповіді SPEC закладає обидва кроки: повторний вхід і перезапуск
служби.

### 9.3 Планувальник

Планувальник — не служба сервера додатків: його раз на хвилину запускає завдання SQL Server Agent, стартуючи
`IT2Client2.exe` під службовим користувачем. Сервер може працювати, а планувальник стояти
(instr, doc_id=124188; help, doc_id=131824).

## 10. Конвенції

- **Коди власних сутностей** починаються з `_` (вимога для RRT-методів, help, doc_id=132241; для об'єктів і
  таблиць допустимо також закінчення на `_`, help, doc_id=132240). Далі — префікс `TD` і мнемоніка доробки
  (A-03): `_TDINV`, `_TDINVCHK`.
- **Довжина:** код таблиці — до 8 символів (поле `TABLENAME` C,8 у `HTMLHELP`, forms, doc_id=124429); код типу
  процесу — до 10 (`DMT.KDMT` C,10, forms, doc_id=124883). Довжина коду RRT-методу невідома (Q-05).
- **Інсталяція вже має чужі `_`-коди:** `_INVR`, `_INVROS` (instr, doc_id=134606), `_SALPAYACB`, `_BST_OUT`
  (help, doc_id=128321). Перед створенням коду — пошук у базі на збіг.
- **Розкладка репозиторію:**

  ```
  docs/                       ARCHITECTURE.md, DOC_STANDARD.md, modules/<доробка>/{ARCHITECTURE,SPEC}.md
  src/csharp/<доробка>/       C#-код: один файл на одне поле BL (src/csharp/README.md)
  src/config/<доробка>/       розібрані пакети конфігурацій (src/config/README.md)
  tools/ite_graph/            граф доробок за таблицями конфігурації (tools/ite_graph/README.md)
  ```

- **Бінарники вендора** (`ITAsseblies`, DLL платформи) у git не кладуться: це ліцензійний код, і їх версія
  прив'язана до інсталяції.
